# Plan: Support `season_id in (...)` for program-agnostic year matching

## Context

The seasons table now stores a **program id per season** (visible in the season knowledge —
each entry has `program.id`). A single calendar year maps to *several* seasons, one per
program. For example year **2025** → `196` (VIQRC), `197` (V5RC), `198` (VURC),
`199` (VAIRC), `201` (AIR Drone).

Previously the parser could only emit `season_id eq <one value>`. That is wrong when the
user names a year but **no program**: there is no single correct season. The parser now:

1. Resolves `program_id` first.
2. **Program known + year given** → emits a single `season_id` with `eq`.
3. **No program + year given** → emits `season_id` with the new **`in`** operator listing
   *every* season that matches that year.

`in` is intentionally scoped to `season_id` only for now; it may be generalized later.

## Changes

### 1. Schema — `schema/__init__.py`
- Add `"in"` to the `op` Literal on `FilterCondition`.
- Widen `value` to `Union[str, int, float, List[Union[int, str]]]`.
- Validator: `in` requires a list value; all other ops require a scalar.

`lambda_handler.normalize()` needs no change (already serializes with `by_alias=True` /
`exclude_none=True`; Pydantic handles list values).

### 2. Prompt — `prompt.md`
- OUTPUT SCHEMA: add `in` to the op enum; `value` may be an array.
- Filter fields: `season_id` supports `eq` (single) and `in` (array); `program_id` stays `eq`.
- `--- Season ---` rules rewritten around program-first logic (eq when program known,
  in-list of all matching seasons when no program).
- Two new examples: program+year → `eq`; year-only → `in [...]`.

### 3. Knowledge base re-chunking — `knowledge/season.md` → `knowledge/seasons/<year>.md`
- One markdown file per year (grouped by `years_start`), each listing every season for
  that year, mirroring the existing per-program chunk + `.md.metadata.json` sidecar pattern.
- Generated by `tools/gen_season_chunks.py`.
- The single `knowledge/season.md` is removed (replaced by the per-year chunks).
- Re-embed / re-index the Bedrock Knowledge Base after the files change (owner: user).

### 4. Retrieval — `knowledge_service.py`
- `numberOfResults` stays at `3` (each year is now one chunk).
- Per-year file heading kept as `# VEX IQ Seasons <year>` so the existing year-injection
  rewrite still steers retrieval to the right chunk (no regex change needed).

## Verification
1. Schema unit check (no AWS): `in` with list validates; `eq` with list and `in` with scalar
   are rejected; SearchQuery with a season `in` filter serializes to `"op":"in","value":[...]`.
2. `python run_local.py` (needs AWS + re-index):
   - "best team in 2025 VIQRC" → `season_id eq 196`.
   - "best team in 2025" → `season_id in [196,197,198,199,201]`.
   - query with no year/program → no season filter.
3. Cross-check emitted id sets against `knowledge/seasons/<year>.md`.
